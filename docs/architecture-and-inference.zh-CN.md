# 架构与推理流程

## 文档目的

本文档说明 `Gemma4.Voice` 如何使用 `onnx-community/gemma-4-E2B-it-ONNX` 来实现 CPU 优先的语音转写。重点关注运行时架构、数据流、模型图拆分方式，以及为什么项目会采用当前这种实现结构。

## 高层流程

从整体上看，转写流程如下：

1. 接收本地音频文件路径
2. 构造“音频 + 文本指令”的多模态提示
3. 用 `Gemma4Processor` 做音频预处理
4. 运行 ONNX 音频编码器
5. 运行 ONNX embedding 图
6. 将音频特征注入文本 embedding 序列
7. 使用带 KV cache 的 merged decoder 做自回归解码
8. 将生成 token 解码为最终文本
9. 如果是时间戳模式，则额外转换成 SRT

这是一个相对显式的推理循环。之所以这么做，是为了让运行逻辑更容易理解，也更容易调试和扩展，而不是把所有行为封装在一个不透明的黑盒里。

## 为什么模型图是拆开的

这个 ONNX 仓库不是一个单一大模型文件，而是拆成多个图。在本项目中，最关键的几个组件是：

- `audio_encoder*.onnx`
- `embed_tokens*.onnx`
- `decoder_model_merged*.onnx`

它们的职责分别是：

- 音频编码器：把声学特征转换成模型空间中的音频特征
- embedding 图：生成文本 token embedding 和每层附加输入
- decoder 图：执行自回归文本生成

这样拆分有几个明显好处：

- 每个组件的职责更清晰
- 某个阶段出错时更容易定位问题
- 更方便后续优化
- 在纯音频工作流中可以直接跳过视觉分支

## Processor 的职责

`Gemma4Processor` 是整个设计中的核心组件，它远不止是一个 tokenizer。

它负责：

- 应用多模态 chat template
- 从输入音频中提取声学特征
- 构建 `input_ids`、`attention_mask` 和音频特征张量
- 保留模型所期望的特殊音频 token 布局

因此，processor 实际上扮演了“用户输入”和“底层 ONNX 图”之间的桥梁角色。

## 音频特征路径

对语音转写任务来说，processor 会生成这样的张量：

- `input_features`
- `input_features_mask`

这些张量会被送入 ONNX 音频编码器。该阶段输出的是 `audio_features`，随后这些特征会被插入到 token embedding 流中，对应模型音频 token 所在的位置。

这是一条非常重要的架构细节：decoder 并不是直接消费原始音频，而是消费一条“类文本序列”，只不过这条序列的 embedding 流里被注入了来自音频编码器的语义特征。

## Embedding 阶段

embedding 图会输出两个关键结果：

- `inputs_embeds`
- `per_layer_inputs`

其中，`inputs_embeds` 是当前生成步的 token embedding，`per_layer_inputs` 则携带了解码器层所需要的附加输入。

在音频编码器得到 `audio_features` 之后，这些特征会被写入到 `inputs_embeds` 中与音频 token 对应的位置，形成最终送入 decoder 的序列表示。

## Decoder 阶段与 KV Cache

merged decoder 图负责执行自回归生成。它需要的输入包括：

- token embeddings
- attention mask
- position ids
- per-layer inputs
- past key/value 张量

每一步解码之后，它会输出：

- 下一步 token 的 logits
- 更新后的 present key/value 张量

这些更新后的张量会在下一轮迭代中作为 `past_key_values` 回灌进去，这就是标准的 KV cache 机制，也是保证自回归生成效率的关键。

如果没有 cache 重用，随着上下文长度增加，每一步生成的成本会迅速变高。

## 为什么项目保留显式循环

理论上可以把这条推理链封装得更短，但项目刻意保留了显式循环，原因很工程化：

- 更容易观察性能瓶颈
- 更容易排查 tensor shape 错误
- 更容易调整停止条件
- 更容易实验不同 prompt 策略
- 更方便以后接批量或流式能力

对于一个面向部署的开源项目来说，这种显式性通常比“更短但更黑盒”的实现更有价值。

## Prompt 模式

项目当前主要暴露两种提示模式：

- `transcribe`
- `timestamps`

模型行为之所以不同，是因为任务指令不同，而不是因为底层解码栈不同。

也就是说：

- 两种模式走的是同一条 ONNX 推理路径
- 真正变化的是自然语言提示词

这也说明了本项目对 Gemma 4 的使用方式：它在这里被当作一个“遵循指令的多模态模型”，而不是一个输出行为被硬编码死的专用语音解码器。

## 时间戳生成与对齐的区别

项目在时间戳模式下输出的时间，是模型根据提示词生成出来的，而不是通过专门的对齐模块计算出来的。

这意味着架构天然支持：

- 类字幕格式输出
- 具有实用价值的分段级时间估计

但并不提供：

- 严格确定性的强制对齐
- 词级时间精度保证

这个区别应该直接影响你对下游产品形态的判断。

## 为什么这是一个 CPU 优先的设计

`Gemma4.Voice` 是刻意围绕 CPU 使用场景设计的，这会影响很多实现选择：

- 优先 ONNX Runtime，而不是通用 PyTorch CPU 路线
- 把 `q4` 变体视作更现实的本地默认配置
- 用纯推理时间计算 `RTF`
- 推理完成后立刻写文件，方便离线工作流

这样能让项目聚焦于真实可落地的本地部署目标，而不是扩展成一个泛化的训练/微调框架。

## 错误处理策略

项目目前采用的是“轻量但显式”的错误处理策略。

CLI 主要捕获：

- 输入文件不存在
- 转写过程中的运行时异常
- 批量模式下没有发现可处理的音频文件

目标不是隐藏错误，而是让失败更明确，并暴露足够的上下文帮助排查问题。

## 批量模式为什么这样设计

批量模式目前并不是把多个音频一次性打包进一个 ONNX 推理调用，而是“对每个文件重复执行单文件转写”。

这是一个有意为之的工程取舍：

- 控制流更简单
- 输出命名更清晰
- 单个文件失败时更容易隔离问题
- 减少多模态 shape bug 的风险

对于目前这个成熟度阶段的开源项目来说，这种实现比过早引入复杂 batch 推理更稳妥。

## 输出设计

输出策略同样刻意保持简单。

对每个输入音频，项目会写出：

- 一个 `.txt` 转写文件
- 如果是时间戳模式，再额外输出一个 `.srt` 字幕文件

默认文件名会包含当前使用的 `variant` 和 `mode`，这样当用户做不同配置对比时，不容易发生文件覆盖。

## 为什么这个结构适合项目当前阶段

这套结构之所以适合 `Gemma4.Voice`，是因为它在以下几个目标之间取得了比较好的平衡：

- 清晰性
- 本地实际性能
- 可扩展性
- 尽量减少隐藏行为

它并不是理论上最短的实现，但从可维护性和可调试性来看，这种结构对一个真实的开源项目通常是更好的折中。
